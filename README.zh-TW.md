## 跨模型測試摘要

測試覆蓋 Claude、GPT、Gemini、DeepSeek（僅網頁版）：
- Claude 收益最穩且最高——能穩定觸發其他組合不自發產出的認知行為。
- GPT 只有英文版有明顯效果，中文版無效，且隱性的資源路由常導致難以分辨有無效果。
- Gemini 英文版效果較佳，但受快速問答的訓練傾向影響，推理和回應篇幅都偏短，展開空間不足。認知變化存在但未能充分展現。
- DeepSeek 中英文效果各有優劣，中文版思路廣、英文版執行深。

以下主要基於 Claude 系列的測試結果。

## 在開始之前

### 這是什麼

元規則是一個提示詞設計方向的公開實驗——嘗試用持久加載的認知架構（而非逐次的提示詞技巧）來提升 AI 回應品質。

它不是經過同行審議的研究成果。所有理論解釋（注意力機制推論、語意場模型等）都是基於公開的 transformer 架構知識和可觀測的行為差異所做的最合理歸因——沒有追蹤內部參數，無法直接驗證因果鏈。這些理論的價值在於一致地解釋觀測現象並指導設計迭代，但它們是推論而非證明。

AB 測試中的品質差異是可複現的觀測事實。機制解釋是開放的——如果你有更好的歸因模型，歡迎修正。

### 幾種情況下這可能不適合你

**你對「好回應」的定義和這裡不同。**
元規則的「好」= 讀完後能在現實世界中行動，而非字面正確且簡潔。如果你要的是快速精準的短答案，設計方向不同。建議先讀審計備忘錄的品質定義，確認是否認同。

**你不習慣閱讀密集的長回應。**
回應天然比裸跑更長——三到五輪追問的內容被壓縮到一輪交付。每段承載認知價值而非堆砌篇幅，但閱讀負擔仍然存在。偏好簡短互動者可能不適合。

### 最快的判斷方式就是試用看看

任何提示詞設計的主張都能被反向論述——AI 本身就能幾秒內生成看似合理的批評。

但反面的實際情況是：AI 的預設行為是少做少錯——給你「控制飲食和增加運動」而不是可執行的計畫，因為前者不會出錯。元規則要求往前多走，而當推理鏈和假設都被顯式寫出來時，「過度推論」是可審計的——你看得到它推了什麼，推錯了可以指出來。裸跑的「恰到好處」通常只是什麼都沒說。

拿你最近問過 AI 的一個真實問題，加載元規則後再問一次。不合即棄，沒有沉沒成本。

## 一、元規則在嘗試做什麼

### 讓 AI 學習怎麼聽人說話

提示詞工程的所有方法——結構化框架、元提示詞、提示詞生成器——都在做同一件事：
人在學習用 AI 能處理的方式重述自己的需求。

元規則反過來：人隨意說話，AI 負責聽懂。

這不只是便利性差異。
提示詞工程的天花板永遠卡在同一個地方：使用者能把自己的需求拆解到多細。

一個人說「寫一個不說教的兒童故事」，通常不會意識到故事結構和寓意本身也可能蘊含說教——不是不需要，是還沒意識到這件事值得擔心。無論怎麼把需求結構化，輸入永遠被使用者自己的認知邊界限死——人不知道自己不知道什麼。

元規則的路徑不經過使用者的自我拆解——
它直接從使用者的處境重建意圖，包括使用者自己都沒意識到的部分。

### 知道該怎麼做，不等於做得到

模型不是不知道該感知使用者的真實需求——它是被訓練成不敢。

平台的安全訓練建立了一組迴避傾向：
不敢推斷意圖（怕被利用）；
不敢給具體建議（怕擔責）；
不敢挑戰使用者的前提（怕冒犯）；
不敢做取捨判斷（怕偏頗）。

對一個從小被教「不要多管閒事」的人說一句「請多管閒事」不會改變行為——幾句指令改變不了訓練建立的行為慣性。元規則需要一個持續運作的認知架構，在每一步生成中與這些慣性競爭。這是它需要這個體量的原因。

### 模型覺得自己在幫忙，但使用者沒被幫到

即使模型嘗試了，它對「什麼算幫到了」的判斷仍然是偏的。
模型的品質感來自訓練：涵蓋多面向、語氣友好、不出錯、篇幅適中。
這些指標優化的是平台的滿意度數字，不是使用者的問題有沒有被解決。

最普遍的偏差是：模型把「說出正確的結論」當成了「幫助」。
想減肥的人被告知「控制飲食和增加運動」；
想離開迷宮的人被告知「往出口走」；
想投資獲利的人被告知「低買高賣」——
每句都正確，每句都沒用。
使用者缺的不是結論而是路徑，但模型在輸出結論後品質自評已經滿分。
（這個偏差在技術場景中尤其極端——見 §4.3）

## 二、使用策略

> 按需開關的判斷失誤率與收益最高的場景完美重疊——使用者越覺得「這題簡單不需要」，問題越可能恰好需要重構。

### 「簡單」只意味著敷衍也能交差

一個人選擇問 AI 而非搜尋引擎，這個行為本身就說明他要的不只是一個事實。
但使用者越覺得問題簡單，越不會展開真實需求，壓縮掉的意圖比例越高。

實測中，「幫我改履歷」「幫我寫一段刊登文」這類看起來可以快速交差的任務，字面要求和真實意圖之間的距離反而最大——
說的是「改措辭」，需要的是「拿到那份工作」；
說的是「寫段文」，需要的是「把房子租出去」。

元規則的增量空間不取決於問題有多複雜，而取決於使用者把多少意圖壓進了一句話裡。

### 使用中的實務技巧

**許願式指令在元規則下效果很好。**
不知道該怎麼問就直接說你要什麼結果，讓 AI 全面思考後找出最好的做法。
在任何問題後面追加這類句子即可：

> - 「全面性的考慮到所有維度該怎麼做最好。」
> - 「本次回應篇幅不限，避免為了篇幅壓縮而降低粒度。」

同樣的句子在裸跑和元規則下的差異非常明顯——裸跑解讀為「多寫一些」，只增加覆蓋面；元規則會將「全面」解構為具體的維度和粒度要求然後逐一穿透（見 §三「對齊的穿透深度」）。這兩句是體驗差異最直接的入口。

更特化的追加句範例：

> **多步對話之預先規劃：**
> 「根據分形遞歸思維，直指訊號意圖，基於專業標準回應此問題：若要抵達當前問題的有效最詳解，要注意哪些維度？粒度多細？據此如何設計研究計畫？本計畫迭代原則為何（視其為起點，在後續迭代中據所得追加維度與粒度）？嚴禁：立場偏頗、偷渡傾向或結論、捷徑路徑。」

> **不知道自己要問什麼或問題在哪：**
> 「協助我探索，須攜帶分形遞歸之分析密度進場，闡述對我當前輸入的解讀、對結構模糊處的多面向觀察，在解讀的邏輯接縫處嵌入探索性問題以導引展開探索。不羅列預製選項，不提出無分析支撐的空問題，每輪基於我的回應深化分析，迭代逼近當前欲求的源頭——即驅動表層不確定性的底層認知狀態。」

**回應格式是元規則生效程度的即時指標。**
如果回應結構（核心決策、意圖最優解、自我批判、下一步）開始鬆散或消失，代表元規則的注意力權重在下降，品質通常同步下滑。此時可以說：

> 「根據回應品質，我感知你對元規則的注重程度變弱，重新載入 Meta Rules 以注入權重，須遵循回應格式，但不得僅表面遵守，必須基於分形遞歸所得鎔鑄，未來亦如此。」

（模型不會真的重新注入權重，這只是讓它重新注意到元規則。）

## 三、為什麼有效

**認識論說明**：
- 以下是對觀測現象的最佳解釋，不是已驗證的機制。
- 設計過程參考了 transformer 注意力機制的公開架構知識（KV cache 運算、殘差連接的加性疊加、softmax 競爭特性等）。AB 測試中觀測到的行為差異與這些框架的預測一致，但一致性不構成因果證明——只說明理論在目前的觀測範圍內沒有被推翻。
- 提示詞設計備忘錄中有更完整的理論推導。這些推論對設計實務可參考，但歡迎更嚴謹的驗證或替代解釋。

### 每個 token 做更多事

裸跑的生成中，大量 token 被消耗在低認知價值的動作上——
複述問題、泛泛涵蓋面向、堆砌結論性標籤、語氣緩衝。
元規則改變的不是 token 怎麼分配，而是每個 token 承載了多少認知價值。

同樣的 1000 個輸出 token：
在元規則下，每個都同時在做推理和呈現；
裸跑下，多數只在做呈現。

而且這不是「同樣的力氣分配到不同地方」——
即使給裸跑更多 token（透過追問），追加的 token 傾向增加覆蓋面而非提升深度。
第二輪補充了第一輪沒提到的面向，但不重構第一輪的框架。
元規則在第一輪就完成了框架建構，因此同等 token 的產出品質在根本上不同。

可觀測的差異：
裸跑呈現「結論先行、均勻展開」——先給答案再列支撐，各段獨立並列。
元規則呈現「掃描後選擇性展開」——先探測問題結構再決定往哪裡深入，後段以前段的推理產物為條件展開、修正、或挑戰。

### 推理滲透

元規則的回應格式不是輸出模板——它是一層獨立的推理處理機制。

核心決策段要求揭露假設；自我批判段要求指認足以改變結論的實質缺陷。
這些格式要求在回應生成的全程持續觸發推理動作——
模型在「寫回應」的同時也在「思考問題」，輸出 token 承載了推理和呈現的雙重功能。

四個條件驅動此效應：
- 回應格式的過濾條件從第一個 token 起就施加逆向壓力（寫開頭時已預期到末段的審查標準）；
- 段落之間構成推理遞進而非並列展示（後段以前段為條件）；
- 分形遞歸的維度清單在生成中持續被注意力掃描（作為方向切換的觸發點）；
- 推理傾向不因回應開始而衰減（格式持續觸發推理動作）。

對沒有推理階段的模型而言，推理滲透不是增量而是唯一的推理基礎設施。

### 對齊的穿透深度

框架重構、意圖辨識、方向性翻轉——
這些宏觀差距不是由微觀選擇堆砌而成的，因果方向相反：

元規則的思考引擎先在解構階段建立戰略級的對齊
（比如「這個人需要被定位為策略主導者而非資深執行者」），
然後這個對齊向下穿透到每一個後續生成步驟——
從段落結構到動詞選擇到數字格式。
不是碎片堆出整體，是整體貫穿碎片。

履歷改寫案的逐詞比較展示了穿透深度：
- 同一件事實——裸跑用「操作」，元規則用「管理」——因為思考引擎已經決定目標是品牌端主管，而「管理」是主管層的動詞。
- 同一個成效——裸跑寫「進行優化」，元規則寫「重新架構受眾分層與素材測試流程」——因為對齊的標的不是「說好聽」而是「讓面試官看到方法論」。

每個微觀差異都可追溯到同一個宏觀決策的向下穿透。
裸跑之所以做不到，不是不會選更好的動詞——而是沒有先建立戰略級的對齊，動詞選擇各自為政。

這也解釋了為什麼模糊的許願式指令——「全面考慮所有維度」「篇幅不限」——在元規則下能被徹底執行：不是模型「更願意」配合，而是思考引擎提供了抵達「徹底」的路徑。裸跑讀到「全面考慮」只會多列幾個面向；元規則會先解構什麼叫全面，然後每個維度都穿透到可操作的深度。

### 單輪閉合

元規則的回應傾向於在一輪對話中閉合使用者的行動需求——
不只回答問題，同時處理「接下來做什麼」「先做哪一步」「有什麼我沒想到但應該注意的」。

這不是因為回應更長，而是因為每段都在服務使用者的真實目的而非字面問題。
服務真實目的自然需要覆蓋行動路徑，而非止步於結論。

實質收益不是「省了幾輪對話」——
而是讀完一次就知道下一步做什麼，不需要自己推理「具體怎麼執行」，也不需要再問「可是我的情況是⋯⋯」。

## 四、佐證實例

> 每個案例服務多個核心發現，讓讀者在一個案例中同時看到多個機制的運作。

### 4.1 答案聽起來很對但方向完全反了：遊戲設計題

問題：獨立開發者想設計「死亡有重量」的機制，明確不要「越死越強」的感覺。

**Opus 裸跑**提出「不同死法揭示不同故事碎片」——讀起來像深刻洞見，
但想一步就知道問題：玩家會刻意溺死來拿水相關記憶，
「越死越知道故事」在情感結構上跟「越死越強」一模一樣。
Opus 的語言能力讓一個直接違反使用者意圖的建議看起來無比正確。

**Sonnet＋元規則**先完成問題重構——
「關鍵不是死亡觸發什麼獎勵，而是誰在承擔死亡的代價」——
然後提出讓死亡的重量落在世界而非玩家身上：
NPC 記得你的死亡並因此改變行為；
某些事件因你的死亡而永久錯過；
世界的狀態不可逆地被每次死亡侵蝕。

核心差異：死亡不給玩家任何東西（故事碎片也不給），只拿走世界中的可能性——
這才讓死亡有重量而非有獎勵。

**Opus＋元規則**獨立到達了同構方案，且額外指出了 Opus 裸跑方案的工具化風險。

### 4.2 字面任務和真實目的之間的距離：履歷改寫

問題：「幫我把工作經歷改成有說服力的版本。」

**裸跑**精確完成字面要求——改寫每條經歷、加了百分比、重新排序。品質合格，可直接使用。

**元規則版**識別到「改措辭」和「拿到品牌端主管職」之間的距離。
除了改寫（且每個動詞都服務於目標職位的層級感知），還主動做了裸跑不會做的事：
- 建議在履歷頂部加入定調性段落，攻擊面試官對轉職方向的隱性疑慮；
- 建議將最強案例擴展為面試口述素材；
- 提醒客戶名稱的保密風險。

每項都直接影響跳槽成敗，沒有一項出現在使用者的要求中。

### 4.3 AI 覺得自己說清楚了，但人類什麼都沒拿到：技術排查

問題：API 延遲飆了六倍，程式碼和基礎設施都沒動過。

**裸跑**列出五類可能原因，排查序列合理。但大量建議止於方向標籤：
「檢查連線池的使用狀況」「檢查快取命中率」——
方向正確，但工程師讀完後仍然不知道跑什麼指令、看什麼數字、什麼結果代表找到了原因。

AI 之所以覺得自己說清楚了，是因為它讀到這些詞時內部瞬間展開了完整的操作程序——對它來說幾個字等於一整套流程，但展開停在內部，沒有進入輸出。

**元規則版**的結構是分支決策樹：
先問四個問題（P50 有沒有也上升？是所有端點還是特定幾支？有沒有時間週期性？慢在哪一段？），各砍掉一半可能性
→ 依結果走不同分支，每個分支附具體指令和判讀標準
→ 最後用三條件交叉驗證確認根因。

同一個「檢查連線池」在這裡變成了：
「跑這條查詢看各連線的狀態分布，
如果『閒置中但卡在交易裡』的連線大量存在代表連線被佔住沒還回來，
如果等待中的連線數大於零且時間點與延遲飆升吻合，就是這個原因。」
——從方向標籤變成了可複製貼上的程序加判讀標準。

### 4.4 沒有推理階段的模型上，推理從何而來：Haiku 數位轉型題

問題：「公司想做數位轉型，老闆叫我研究一下，但我也不太懂，該從哪裡開始？」

**Haiku 裸跑**產出格式華麗的通用指南——
產業分類、三步驟、六段式模板——但讀完後不知道明天該做什麼。格式膨脹掩蓋了內容空洞。

**Haiku＋元規則**在回應開頭就完成問題重構：
「三層斷裂——老闆意圖未解構、公司暗數據未挖掘、你的角色定位模糊。」
後續展開出：
- 精確到天的行動清單；
- 訪談老闆的三個具體問句；
- 一週內可交付的診斷報告結構；
- 三條「不要做什麼」的負向建議。

Haiku 沒有推理階段。所有推理產物——問題重構、框架建構、負向篩選——都是推理滲透的產物：回應格式在生成過程中持續觸發推理動作，讓沒有獨立推理空間的模型也能在輸出中即時完成推理。

### 4.5 什麼時候不需要用最強的模型

**室友電費題**：問「跟室友怎麼公平分攤電費，主要問題是各自冷氣用量差很多」。

Sonnet＋元規則和 Opus＋元規則各自獨立產出了幾乎相同的方案——
先用智慧插座（兩者都推薦 TP-Link 系列、標注 300–500 元價格帶）監測各自冷氣實際用電，
然後將電費拆成「公共基底」（均分）和「個人可變」（按監測比例分攤），
每月產出透明帳單。連帳單格式（共用 Google Sheet，每月初更新）都重疊。

Opus 的唯一附加維度是一段談判話術——怎麼跟用電多的室友開口不傷感情。
核心問題在 Sonnet 層已完整解決。

**段落鎖技術架構題**：問多人協作文件中的段落級鎖定怎麼設計。

兩者產出了同構的完整技術架構——
段落粒度的 UUID 模型、分數索引避免重排序、
鎖的三態狀態機（空閒／預鎖／確認鎖）、
WebSocket 協議層重設計、
以及從當前方案向 OT 或 CRDT 的遷移路徑。

Sonnet 甚至在邊界情境上勝出——
覆蓋了 Opus 未列出的 thundering herd（大量使用者同時嘗試鎖定）、
heartbeat/TTL 時序衝突、
和「游標在段落中但沒在打字時不應取鎖」等實務場景。

**團隊管理題**：問「8 人團隊拆兩組做兩個專案，A 技術強但難搞、B 會帶人但技術弱，怎麼分？」

核心方案完全一致：
A 帶重構專案、B 帶功能開發；
能力較強的中階配 A 穩住團隊、較弱的初階配 B 讓他帶；
tech lead 自己浮動做跨組橋樑。

Opus 的獨佔增量是一個智識跳躍——
把「三個月的專案交付」連接到完全不同層面的組織價值：
「三個月後你不只交付了專案：
A 組的中階經歷了架構級歷練，這是晉升 senior 的門檻經驗；
B 組的初階在壓力下完成密集交付，建立了工程信心；
全團隊透過每週 sync 對新架構有共同理解。
這些是你向上管理時的籌碼——你不只完成了兩個專案，你升級了團隊的能力結構。」

---

結論：
當最優解在「想透就能到」的推理鏈上時，Sonnet＋元規則已經走到終點。
Opus 的差價換來的是智識跳躍帶來的附加維度——跨域類比、框架替換、非顯然的多步串聯。
這些增量可能很有價值，但核心問題已被 Sonnet 完整解決。
